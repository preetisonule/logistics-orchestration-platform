📝 Kafka — Architecture & Event Contract Specifications

Apache Kafka is the event-streaming backbone for our Distributed Logistics Orchestration Platform.

========================================================================================
🔑 Key Concepts in Our Implementation
========================================================================================

Producer: Microservice publishing domain events via Transactional Outbox.
Consumer: Independent microservice processing events.
Topic: Dedicated event streams (`inventory-events`, `warehouse-events`, `carrier-events`, `shipment-events`).
Partition: Partition keying maintains message ordering per entity (`inventoryId`, `taskId`, `shipmentId`).
Consumer Group:
  - Same Consumer Group = Competing consumers (load balancing across instances).
  - Different Consumer Groups = Independent consumption (e.g., Warehouse Service vs Event Store Service).
Offset: Sequential position tracker per consumer group in partition log.
Event ID: Global unique identifier (`eventId`) for idempotency enforcement.
Correlation ID: Distributed tracing identifier (`correlationId`) tying an entire order lifecycle together.
Causation ID: Upstream parent event identifier (`causationId`) indicating what triggered the event.

========================================================================================
📜 Standard Event Envelope Contract
========================================================================================

All events emitted to Kafka use the standard EventEnvelope structure:

{
  "eventId": "uuid",
  "eventType": "INVENTORY_RESERVED",
  "version": 1,
  "occurredAt": "2026-09-19T12:00:00.000Z",
  "source": "inventory-service",
  "correlationId": "uuid",
  "causationId": "uuid",
  "data": { ... }
}

🔄 Workflow Stream
========================================================================================

Inventory Service (POST /inventory/:id/reserve)
       │
       │ INVENTORY_RESERVED (key: inventoryId)
       ▼
     Kafka (inventory-events)
       │
       ▼
Warehouse Service (Idempotent task creation)
       │
       │ PATCH /tasks/:id/status -> PACKAGE_READY
       │ PACKAGE_READY (key: taskId)
       ▼
     Kafka (warehouse-events)
       │
       ▼
Carrier Selection Service (Priority & Weight Evaluation)
       │
       │ CARRIER_SELECTED (key: taskId)
       ▼
     Kafka (carrier-events)
       │
       ▼
Shipment Service (Idempotent shipment creation)
       │
       │ SHIPMENT_CREATED / SHIPMENT_STATUS_UPDATED
       ▼
     Kafka (shipment-events)
       │
       ▼
Event Store Service (Consumer group: event-store-service-group, fromBeginning: true)
       │
       ▼
PostgreSQL event_db -> GET /events -> React Operations Dashboard

========================================================================================
🛡️ Reliability Patterns
========================================================================================

1. Transactional Outbox Pattern:
   Database updates and outbox insertions occur inside a single ACID transaction (`prisma.$transaction`).
   A background non-overlapping loop publishes events to Kafka with retry tracking (`attempts`, `lastError`).

2. Idempotent Consumer Processing:
   Kafka guarantees at-least-once delivery. Downstream consumers track `sourceEventId` or `taskId` with database-level `@unique` constraints to safely ignore duplicate deliveries.
